- (note) Source: Epic 1 (Claim Decisions Recorded, FR1-5) from the epics-breakdown conversation for Case Expenses, itself derived from prd.md and SPEC-expense-claim-reviewer/SPEC.md (parent case spec) and ARCHITECTURE-SPINE.md. Epic 1 covers CAP-1 through CAP-6 of the parent spec; CAP-7 (explain) and CAP-8 (eval) belong to Epic 2, out of scope here
- (decision) Why: Finance needs every claim line item decided consistently against POLICY.md and recorded, with big payouts visibly gated - this epic delivers the deterministic decide-and-record pipeline everything else (explanation, eval, Epic 2) builds on
- (capability) CAP-1 (reused id from parent spec): Assemble claim context - intent: given a claim_id, fetch employee+line items (get_claim), employee level/city (get_employee), category limits (get_policy_limits); success: matches seed data for all 40 claims
- (capability) CAP-2 (reused id): Decide each line item under POLICY.md's fixed precedence order (3, 5.1, 1.2, 4.1, limits 2&6, 1.3, else category default); success: decision+clause match eval/labelled.csv on all 30 labelled claims, and generalizes (no claim/line/employee-id branching) to the unscored holdout
- (capability) CAP-3 (reused id): Aggregate per-window before applying limits (2.4) - meals(2.1)/ground(6.1) summed per day across a claim's lines; hotel(2.2)/flight(2.3) judged per line, never summed; success: per-day/per-line totals produce the approve/flag/reject split implied by labels
- (capability) CAP-4 (reused id): Detect duplicate line items (5.1) within one claim (same employee, date, merchant, amount), same-date ties broken by ascending line_id; success: all 3 duplicate pairs in seed data resolve to reject/5.1 on the higher line_id
- (capability) CAP-5 (reused id): Record every decision idempotently via record_decision(line_id, decision, clause), upsert keyed on line_id; success: running the agent twice leaves exactly one unchanged row per line item
- (capability) CAP-6 (reused id): Any approve-decision line item over $500 is identifiable as pending human sign-off via a derived filter (decision='approve' AND amount>500), never a stored state; success: every such item is correctly identifiable by that filter, none require a schema change to find
- (constraint) Decision-making is deterministic, not LLM-authored (Spine AD-1): decision_engine.py implements POLICY.md's precedence order in plain code with no branching on specific claim/line/employee ids; the LLM (Epic 2's concern) never picks the decision or clause
- (constraint) decisions table has exactly (line_id, decision, clause); record_decision is an upsert keyed on line_id (Spine AD-2, AD-3)
- (constraint) Exactly four MCP tools (get_claim, get_employee, get_policy_limits, record_decision); decision_engine.py is a plain internal module, never a 5th tool (Spine AD-5)
- (constraint) get_policy_limits(level, city) returns {category: Decimal(limit_cad)} (Spine AD-11)
- (constraint) All currency arithmetic uses Decimal, never float, including across the MCP JSON-RPC wire as strings (Spine AD-8)
- (constraint) Own SQLite file cases/expense/app.db, separate from Saturday's root app.db; nothing here imports/writes to root mcp/, run_agent.py, or root app.db (Spine AD-6)
- (constraint) Full agent runs truncate decisions before starting over all 40 claims; a partial/debug run is not eval-safe (Spine AD-12)
- (constraint) cases/expense/BRIEF.md, POLICY.md, seed/*.csv, and eval/labelled.csv are read-only
- (constraint) cases/expense/INTENT.md must be written before implementation begins, per root AGENTS.md's Sunday rules
